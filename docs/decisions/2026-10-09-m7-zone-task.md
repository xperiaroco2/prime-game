## Context
#36 asks for a second task type, "stand in a zone for N seconds", as the test case of the task system: one new
task-type class, data and a map marker, and no change to the core loop. Its acceptance asks three questions first:
does leaving the zone reset or pause the timer; can two players share a zone; do ghosts count (the issue: they should
not). It adds unit tests and a bot scenario.

What already holds:
- **Tasks are shared** (#79): nobody owns a task, any living player does any subtask, each task type has its own
  subtasks setting, and the `tasks` setting says how many types a match draws from the mode's pool (1 today: one type).
- **"Living" means ALIVE** (vision revision 1, V4): wherever a rule says living, who does subtasks included, it never
  means the downed. There are no ghosts: the dead have no avatar and send no claims, and every range rule reads only
  the last accepted claim (ARCHITECTURE §7.1.2), so a dead player stands nowhere.
- **Open knowledge** (GDD §1, pillar): the fixed places, the task circles among them, are known to everyone. Every
  living or downed avatar's position reaches every player (ARCHITECTURE §5; nothing is hidden behind walls).
- **The engine's slots** (ARCHITECTURE §9.3): a `TaskType` subclass with its `TaskState` as an inner class;
  `TaskTicks` already runs every task type's `tick` in Round, after `LifeTicks` and `ChannelTicks` and before the
  match clock; a `StationKind` (spawn tag, radius, height, palette), whose markers `MarkerReader` snaps to the floor and
  which `CircleViews` draws for whichever task type holds it; `StationPlaced`, `TaskState` and `TaskProgress` are
  generic; `Tasks.subtask_done` is the one way a subtask completes.
- **The paper test** (ARCHITECTURE §9.8): one task-type class; one event class more if the time in the zone is shown
  live, one more if a done zone is shown to everyone; "its time in the zone can run on the channel primitive".

## Decision

### 1. The shape
One task type, `ZoneTask` (`core/tasks/zone_task.gd`; the class name is technical, while the task's id, name and
description are the engineer's, ZD7). Its deal places one zone per subtask: a station of its own `StationKind` on a
distinct random marker of that kind's spawn tag, in a distinct random palette colour, as Delivery places its circles.
Its tick, which `TaskTicks` runs, adds one host tick to each undone zone with a living player inside. A zone whose time
reaches the task's seconds is done, through `Tasks.subtask_done`. The time lives in the task state. One event class is
new: `ZoneProgress`, public, sent only when a zone starts or stops counting, is reset, or is done.

| Need | Part | New? |
|---|---|---|
| The task, its deal and its tick | `ZoneTask extends TaskType`, `has_tick()` true | the one new part class the test allows |
| The time per subtask | `ZoneTask.State extends TaskState`: per subtask its station, its counted ticks, whether it counts now, whether it is done | an inner class |
| The zone | a `StationKind` sub-resource: spawn tag, `radius_m`, `height_m`, palette | data |
| How many zones | the type's own subtasks setting, a whole-number `SettingSpec` of the mode | data |
| Running every tick | `TaskTicks` in Round | exists |
| Inside a zone | Delivery's cylinder test, moved to `StationState` (ZE2) | a move, no new class |
| Live progress and a done zone | `ZoneProgress` (everyone; ZE4) | one new event class |
| Completion | `Tasks.subtask_done`: `TaskState`, `TaskProgress`, the fact `subtask_done` | exists |
| The markers | `MarkerReader` snaps every station kind's markers to the floor; `DealTasks` sums the demand for the fit check | exists |
| Drawing it | `CircleViews` draws any station kind that a task type holds | exists; the look and the fill are M7-Z4 |

`Match`, the phase loop, `DealTasks`, `RuleRunner` and the movement rule do not change: the paper test passes as it
predicted, with the one event class it named for live progress, which here also carries "done" (§Alternatives).

### 2. The rules, if every recommendation is taken
M7-Z1 builds these unless the engineer answers otherwise (§5). Each is revertible in that issue's code or in the data.
1. A match that draws the zone task deals N zones, N its subtasks setting, whatever the player count. Zone i is
   subtask i, in station-id order, which follows the markers' level order. With N = 0 the task has no subtasks and is
   done (#79).
2. Every tick of a phase that lists `TaskTicks` (Round in the base mode), for each undone zone in station-id order,
   the zone **counts** when at least one living player (life ALIVE, any role) stands inside it: the feet of its last
   accepted claim are inside the zone's cylinder, within the radius horizontally and from the floor up to the height,
   edges included, as for a delivery circle, and that claim is at most 10 host ticks old (ZE10: a client that stops
   claiming stops counting). A counting zone gains one tick.
3. A zone whose ticks reach its time (the seconds converted once by the one rounding rule, ARCHITECTURE §3.3; at least
   1 tick) is done: counted for good, shown as done, its subtask done.
4. Leaving **pauses** it: a zone that stops counting keeps its ticks and goes on from them when a living player
   stands in it again (ZD2).
5. Two or more living players inside count as one: a zone gains at most one tick per tick (ZD4).
6. Only where living players stand matters. Carrying, using, swapping, raising, a jump that stays within the height
   and a hit that does not knock down change nothing (ZD9).

### 3. What everyone sees
Everything about the zone task is public, as Delivery is (#79), and the leak test's "every player receives the same
task events" covers it (ZE6).

| What | Who learns it | How |
|---|---|---|
| Where each zone stands, its kind and its colour | everyone | `StationPlaced` in the deal, as the circles |
| Who stands in a zone | everyone | the snapshots: every living or downed avatar is public |
| A zone's time so far, and whether it counts now | everyone | `ZoneProgress` on each change (ZE4); between changes a client draws the fill from its estimate of the host tick, as it draws the match clock |
| A zone done | everyone | `ZoneProgress` at its full time, then the task's `TaskState` and `TaskProgress` |
| Which player made it count | nobody, through an event: `ZoneProgress` names no player | the snapshots show who stood there, as for a delivery |

Two of the recommendations keep it public without a leak:
- **Counting is role-blind** (ZD3). If only the crew counted, a dissident standing alone in a zone would keep it from
  counting, and `ZoneProgress`, sent to everyone, would tell every player that player's role: ARCHITECTURE §9.2's "a
  public event can reveal its rule's owner", here through a condition on the role. Any living player counting
  reveals nothing.
- **A hit does not stop a zone** (ZD9). Hits are private: `Damaged` reaches the victim alone, and #32 rules out hit
  confirmation but for two accepted exceptions (a knockdown, a raise stopped in the tick of a swing). A zone that
  stopped on a hit would send a public `ZoneProgress` in the tick of the swing, a third exception nobody chose. A
  knockdown stops it, but `KnockedDown` is public already.

### 4. Interruptions
With the recommendations. Each row is a unit test of M7-Z1.

| What happens | The zone | Why |
|---|---|---|
| The last living player inside walks out, is pushed out (ARCHITECTURE §7.1.6) or jumps above the height | stops counting and keeps its ticks (ZD2) | the rule is "stand in it". With a pause, a push or a jump costs only the ticks outside, so no grace period (another number) is needed |
| That player is knocked down inside | stops counting in the same tick: the hit's command and `LifeTicks` run before `TaskTicks` | V4: the downed are not living. Otherwise a knockdown would not stop the task, and the knife would be no answer to it |
| It dies or leaves the match | stops counting | the dead stand nowhere; a player who left is not present |
| A downed player crawls into a zone, or is raised inside one | counts from the tick the revive makes it living | V4 |
| A dead player respawns inside a zone (still invulnerable or not) | counts from its respawn tick | it is living; ZE9 keeps zones clear of respawn points, so this needs a respawn point the level placed too near |
| A hit that does not knock down | nothing | no hit confirmation (§3) |
| The player inside picks up, puts down, swaps, swings or raises someone | nothing | standing is not an action; a channel would stop on each of these (§Alternatives) |
| A second living player enters, or one of two leaves | nothing: one tick per tick | ZD4 |
| Round ends, whatever the outcome | nothing more counts: `TaskTicks` runs only in Round, and the ticks stay in the task state until `ResetMatch` | the task state belongs to `MatchState` (ARCHITECTURE §9.1), not to the phase object |
| A client stops sending claims while inside (a freeze, or a modified client that goes on polling) | stops counting 10 ticks after its last accepted claim; counts again from its next accepted claim, if that one is inside (ZE10) | its avatar still stands there on every screen, but no timeout ends this: a client that polls sends keepalives ([the M6 design](2026-10-04-m6-playable-over-the-internet.md) §2.6), so only a hung one is dropped, after 20 s. Counting its stale position would let a modified client earn zone time while its stored credit pays for walking elsewhere (ZE10) |
| A zone reaches its time in the clock's last tick | it is done, and a crew win holds: the tick systems run before the clock (ARCHITECTURE §3.3) | as a delivery in the last tick |

### 7. Testing
- **Unit tests** (M7-Z1, from fixtures only, never `content/`, ARCHITECTURE §9.6): the deal (markers, colours, ids,
  N = 0, a short map logging a match error as Delivery's does), the demands and the fit check, ZE3's mode checks, every
  row of §4 (the freeze row: 200 silent ticks inside, then one claim that spends the credit to walk away; the

## Alternatives
- **The time on the channel primitive** (ARCHITECTURE §9.8 said it "can run on" it). A channel starts only from a
  player's intent (`ChannelEffect.run` refuses a start from no command), is one per actor, stops on any applied action
  of its actor and on a hit, and keeps its progress in the `Channel`, which a stop removes. Standing is not an action:
  a player would need a key to start working (ZD1 (b)), a raiser could not work a zone, a hit would confirm itself in
  public (§3), and a pause would need the effect to copy its ticks into the task state anyway. Rejected with ZD1 (a);
  if the engineer picks ZD1 (b), it is the channel after all, with a `ChannelEffect` subclass and an `InZone` condition.
- **The time in the per-part state table or in the phase object.** The task state is its documented home (ZE1), and
  the phase object dies with Round.
- **Progress in the snapshot, or an event every tick or every second.** ZE4.
- **A generic `StationDone` event for both task types.** Delivery's `PackageDelivered` already marks its circle done,
  so a generic event would change Delivery's events and its wire row for no gain now; `ZoneProgress` carries "done".
- **Counting only the crew.** A public role reveal (§3, ZD3).
- **A grace period before a reset.** Only needed with a reset (ZD2 (b)), and it is one more number.
- **A line-of-sight check from the zone's marker.** It adds `WorldQuery` answers to every tick's log for a question a
  level convention answers (ZD10).
